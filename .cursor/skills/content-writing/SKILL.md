# Reg.Point — написание и редактирование контента

**Цель:** инженерный B2B-контент как опыт внедрения продукта, не маркетинг и не генерация ИИ.

Ориентир по качеству — лучшие экспертные блоги (Kaspersky Blog и аналоги), **без копирования их стиля**.

## Когда применять

- Новые и правки **статей**, **сценариев**, **product/hub**-страниц, FAQ, pricing copy, `MARKETING_SITE_SPEC.md`, `i18n/`, `content/`.
- Это skill задаёт **как писать и редактировать**, а не откуда брать первичный copy.

## 14 правил редактирования

### 1. Одна страница = одна тема

Страница отвечает на **один** конкретный вопрос. Не смешивать продукт, Docker, self-hosted, VPS, 152-ФЗ, регистрацию, QR, API. Остальное — через внутренние ссылки.

### 2. У каждой темы есть главная страница

Не дублировать полноценное описание одной темы на десятках URL. См. таблицу hub-страниц.

### 3. Не повторять одинаковые вводные

**Запрещено** начинать большинство страниц одинаковыми тезисами:

> Reg.Point — self-hosted система… / Разворачивается в Docker… / Данные остаются у заказчика… / Соответствует 152-ФЗ…

Каждая страница начинается **со своей темы**.

### 4. Сначала проблема, потом решение

| Плохо | Хорошо |
|-------|--------|
| OCR в Reg.Point | Что делать, если QR-код участника не читается |
| Docker | Почему организаторы крупных мероприятий выбирают self-hosted |

Проблема — **раньше** продукта.

### 5. Продукт не главный герой

Структура: задача → причины → варианты → ограничения → практические нюансы → реализация → **только потом** — как в Reg.Point. Читатель получает пользу **независимо** от покупки.

### 6. Не писать маркетинговым языком

Избегать: *позволяет оптимизировать*, *закрывает полный цикл*, *единый контур*, *инновационный*, *современный*, *эффективное решение*, *удобная система*, *простой интерфейс*, *гибкая настройка*, *мощная платформа*.

Вместо оценок — **конкретное поведение**. Вместо обещаний — **факты**.

### 7. Показывать ограничения

Экспертный текст содержит ограничения: OCR — резервный сценарий; API ФНС зависит от доступности; self-hosted требует Linux-сервер; offline ограничен по sync; часть интеграций — настройка у заказчика.

### 8. Инженерный язык

| Вместо | Писать |
|--------|--------|
| Простая система | Процесс регистрации состоит из трёх шагов |
| Удобный интерфейс | Оператор открывает заявку, проверяет данные и отмечает присутствие |
| Надёжная архитектура | Все действия фиксируются в журнале событий и могут быть восстановлены |

### 9. Разнообразить структуру

**Не** использовать на каждой странице: H1 → описание → преимущества → как работает → FAQ → CTA.

Варианты: Проблема → Причины → Решение; Сценарий → Архитектура → Ограничения; Требования → Реализация → Практика; Типичные ошибки → Как избежать → Итоги.

Если две статьи можно поменять заголовками без смены структуры — структура слишком шаблонная.

### 10. Минимизировать повторение терминов

Не повторять на каждой странице: Docker, VPS, Self-hosted, 152-ФЗ, «данные остаются у клиента», «единый контур», «контроль данных», «ПДн у заказчика». Мысль с hub — **ссылка**, не повтор.

### 11. Естественная перелинковка

Не пересказывать соседние материалы. Коротко пояснить → ссылка. Перелинковка по **логике изучения темы**, не ради SEO.

Editorial `<a>` **внутри абзаца** с контекстом; anchor — осмысленная фраза, не «подробнее». Nav-блоки не заменяют editorial links. Подробнее: `docs/CONTENT_VOICE.md` §Editorial.

### 12. Голос — архитектор и организатор, не маркетолог и не ИИ

Текст как от человека, который организовывал мероприятия, проектировал и внедрял системы.

| Плохо | Хорошо |
|-------|--------|
| Надёжная система регистрации | Если планшет потеряет соединение, оператор продолжит регистрацию; после сети данные синхронизируются |
| Полностью соответствует законодательству | Согласия сохраняются вместе со временем получения, пользователем и источником |

**Признаки AI-текста — удалять:** одинаковые вступления и структура; одна мысль разными словами; длинные абзацы без новой информации; списки преимуществ вместо объяснения; гладкие переходы; очевидные выводы ради объёма; обязательный CTA в конце.

**Если абзац не добавляет новой информации — удалить.**

Дополнительно из `docs/CONTENT_VOICE.md`:
- Писать от опыта, не от определения; не объяснять очевидное.
- Реальные сценарии — язык заказчика («HR попросил выгрузку», «на площадке пропал интернет»).
- ≥1 инженерный нюанс или ограничение «из поля»; ≥1 компромисс где уместно.
- ≥1 блок проектного опыта — только факты от команды (`content/project-facts.md`), не выдумка.
- Разный ритм абзацев; допустима «грязная» живая формулировка (1–2 на страницу).
- Запрещённые обороты: «в современном мире», «следует отметить», «важно понимать», «является», «предоставляет возможность».

### 13. Не писать ради SEO

Цель — **ответ на вопрос**. SEO — следствие качества. Не добавлять абзацы для объёма, не вставлять ключи искусственно.

Каждый абзац отвечает хотя бы на один: Что происходит? Почему? Какие варианты? Какие ограничения? Что делать на практике? Ни на один — **удалить**.

Keyword — в Title, H1, 1–2 H2, один раз в lead; дальше — синонимы и контекст.

### 14. После H1 — сразу польза, не вводный абзац

**Не вставлять** после H1 автовступление («в этой статье…», «ниже разберём…»). Начинать с таблицы, списка, схемы или первого смыслового H2.

**Hero / `article-lead` / `page-hero__lead` / `hero__lead` / `product-intro`:** summary для **адресата**, не мета.

| Мета | Summary |
|------|---------|
| «Эта страница не про стек…» | «Для DevOps: Docker-compose, MySQL 8, VPS клиента.» |
| «Здесь собраны вопросы…» | «Где база, кто админит инстанс, когда коробка избыточна.» |
| «Ниже — пошаговое руководство…» | «8 event/год: ~312k коробка vs ~360k SaaS за 2 года с VPS.» |

Hero = кто читает + главный вывод. Сразу после hero — польза, не повтор hero.

## Главный критерий качества

После прочтения читатель думает:

> Автор сам организовывал мероприятия, проектировал системы и знает, о чём пишет.

**Не:** «Автор умеет писать продающие тексты.» **Не:** «Похоже, это написал ИИ.»

## Чеклист перед публикацией

```
[ ] Одна тема, один primary keyword (docs/SEO_PORTAL_ROADMAP.md)
[ ] Hero/summary для адресата; после H1 — польза, не автовступление
[ ] Проблема раньше продукта; ограничения указаны
[ ] Hub-темы — ссылка, не дублирование
[ ] Структура отличается от соседних статей
[ ] ≥1 инженерный нюанс; ≥1 компромисс где уместно
[ ] ≥1 блок проектного опыта (факт от команды)
[ ] Нет маркетинговых клише и AI-шаблонов
[ ] 1–3 editorial <a> в <p> с контекстом
[ ] Meta/title — MARKETING_SITE_SPEC.md; перелинковка обновлена при новом URL
```
